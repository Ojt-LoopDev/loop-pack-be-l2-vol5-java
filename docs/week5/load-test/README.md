# 5주차 부하 측정 — 설계한 규칙과 회복이 어디까지 버티나

과제 범위 밖에서 한 측정이다. 확인하려는 가설은 하나다.

> 부하가 아무리 커져도 우리 시스템은 **느려지거나 거절될 뿐, 틀린 결과를 만들지 않는다.**

그래서 두 가지를 같이 본다.
1. **어디서부터 느려지거나 거절되나** — k6 응답 시간·실패율, DB 커넥션 풀, Tomcat 스레드
2. **끝난 뒤 규칙이 지켜졌나** — `invariants.sql`의 "규칙이 깨진 상태" 쿼리가 모두 0건

## 단계

PG 장애를 하나씩만 넣는다 — 원인을 분리하기 위해서다. 먼저 장애 없는 기준선을 잰다.

| 단계 | 테스트 PG 상태 | 확인할 것 | 대비한 회복 경로 | 상태 |
|---|---|---|---|---|
| 0 | 정상: create 바로 202, 1초 뒤 callback, 조회 SUCCESS | 우리 시스템만의 한계 | — | **완료** |
| 1 | callback 안 옴 | 회복 작업이 미종결을 다 회수하나 | 스케줄러(ⓑ) | 예정 |
| 2 | create 응답 3초 지연(timeout 2초를 넘김) | UNKNOWN이 쌓이고 고객 응답이 얼마나 늘어나나 | 바로 재조회(ⓐ) | 예정 |
| 3 | 조회 5xx | 회로가 열리고 상태가 유지되며, 복구 뒤 다시 회수되나 | circuit breaker, D-044 | 예정 |

## 실행 순서

```bash
# 1) 인프라 (kafka는 쓰지 않으므로 끈다)
docker compose -f docker/infra-compose.yml up -d && docker stop kafka-ui kafka

# 2) 테스트 PG (WireMock standalone, 18080)
docs/week5/load-test/pg-stub/pg-stub.sh start
docs/week5/load-test/pg-stub/pg-stub.sh stage 0          # 단계를 바꾸면 받은 요청 기록도 비운다

# 3) 앱 — seed 프로필로 상품 1만 개(재고 각 100)·사용자 500명(포인트 1,000,000). 띄울 때마다 스키마를 새로 만든다
./gradlew :apps:commerce-api:bootRun --args='--spring.profiles.active=local,seed --spring.jpa.show-sql=false --server.tomcat.mbeanregistry.enabled=true'

# 4) 측정 — VU마다 1분, 지표를 1초마다 기록
docs/week5/load-test/run-ladder.sh 0 10 50 100 200

# 5) 회수가 끝나면 규칙 확인 (위 6개가 모두 0, 4번은 pg-stub.sh count와 같아야 한다)
docker exec -i docker-mysql-1 mysql -uapplication -papplication loopers < docs/week5/load-test/invariants.sql
docs/week5/load-test/pg-stub/pg-stub.sh count
```

| 파일 | 내용 |
|---|---|
| `k6/confirm.js` | 주문 생성 → 확정을 쉬지 않고 반복. 사용자·상품을 무작위로 고르고, 삭제 상품은 고르지 않는다 |
| `pg-stub/stage0~3/` | 단계별 WireMock 응답 규칙. `pg-stub.sh stage N`이 그대로 올린다 |
| `invariants.sql` | 규칙이 깨진 상태를 세는 쿼리 |
| `sample-metrics.sh` | 1초마다 `/actuator/prometheus`에서 커넥션 풀·Tomcat 스레드 기록 |
| `results/` | 단계별 k6 요약(`.json`·`.txt`)과 지표(`-metrics.csv`), 회수 진행(`-drain.csv`) |

### 테스트 PG의 한계
WireMock은 상태를 기억하지 못한다. 그래서 거래 키에 금액을 넣어(`TEST-TX-{주문 식별자}-{금액}`) 단건 조회가 키에서 금액을 꺼내 답한다. **키를 모르는 목록 조회(UNKNOWN 결제)는 금액을 알 수 없어 빈 목록**으로 답한다 — 단계 2에서 UNKNOWN은 실제 PG와 달리 0건으로 남는다.

## 단계 0 결과 (2026-10-23, 로컬 PC, Docker MySQL 8.0, DB 커넥션 풀 40, Tomcat 스레드 200)

### 어디서 느려지나

| VU | 처리량(건/초) | 확정 p50 / p95 / p99 (ms) | 실패 | DB 커넥션 사용 / 대기(최대) | Tomcat 스레드(최대) |
|---|---|---|---|---|---|
| 10 | 38.9 → 49.5 | 174 / 301 / 494 → 135 / 221 | 0 | 16 / 0 | 16 |
| 50 | 72.6 → 95.4 | 498 / 728 / 1,012 → 371 / 590 | 0 | **40 / 20** | 60 |
| 100 | 86.1 → 106.4 | 839 / 1,341 / 1,632 → 687 / 1,060 | 0 | 40 / 71 | 110 |
| 200 | 86.0 → 104.8 | 1,697 / 2,745 / 3,490 → 1,392 / 2,177 | 0.02% → 0 | 40 / 161 | **200 / 200** |

(왼쪽: 첫 측정, 오른쪽: D-047 반영 뒤 재측정. 확정 경로는 바꾸지 않았으므로 차이는 측정 회차·JVM 예열에 따른 편차로 본다.)

- **DB 커넥션 풀이 먼저 바닥난다.** VU 50부터 40개가 모두 쓰이고 대기가 생긴다. VU 100부터 처리량이 더 오르지 않고 응답 시간만 VU에 비례해 늘어난다(리틀의 법칙: 200 ÷ 초당 86건 ≈ 2.3초).
- PG 호출은 트랜잭션 밖이고 OSIV도 꺼져 있다. 그래도 결제 한 건이 트랜잭션을 여러 번 쓴다(주문 생성, TX A, 수락 기록, 응답용 조회, callback 저장).
- 첫 측정 VU 200의 실패 2건은 커넥션을 3초 안에 얻지 못한 500이다. 롤백돼 결과는 틀어지지 않았다. 그중 1건은 create를 보낸 뒤 수락 기록을 저장하지 못해 REQUESTED로 남았다(회복 작업 대상).

### 회복 작업이 따라잡나 — 측정이 찾은 결함과 고친 결과

| | D-034 (회차당 100건) | D-047 (초당 20건 상한, 밀린 게 없을 때까지 계속) |
|---|---|---|
| 부하 직후 밀린 callback | 17,080건 | 21,180건 |
| 실제 처리 속도 | 3분에 100건 | **초당 약 13.3건** (상한 20은 한 번도 걸리지 않음) |
| 다 비우는 데 | 약 8.5시간 (추정) | **약 26.5분** (실측, `results/stage0-drain.csv`) |

- 회차당 상한은 깨어날 때 초당 약 50건을 몰아 보내고 178초를 쉬었다. PG 부담(순간 최대)은 크고 처리량은 작았다 → 상한의 단위를 초로 바꿨다(D-047).
- 바꾼 뒤 속도를 막은 건 상한이 아니라 **한 건씩 차례로 처리하는 구조**다. 한 건마다 PG 조회 → TX B → 일정 기록 → 수신함 정리를 차례로 해 약 75ms가 든다.
- 26.5분은 회복 감시 알림 기준(15분, D-035)을 넘는다. 이번 부하는 VU 200을 1분 동안 계속 넣은 극단적인 경우다. 병렬 처리·트랜잭션 합치기는 보류했다(`design.md` 8번).

### 규칙
두 측정 모두 `invariants.sql` 6개 **0건**. 재측정에서 결제 21,580건이 모두 CONFIRMED로 끝났고, 테스트 PG가 받은 create 21,580건 = 결제 시도 21,580건, 충돌 0건, 회복 처리 실패 0건.
