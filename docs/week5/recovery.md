# 5주차 회복 전략 — 확인하지 못한 결제를 누가, 언제 끝내나

`design.md`의 D-005~D-009를 실행하는 방법과 **측정 전 수치**를 모은다. 여기 있는 숫자는 실제 PG 데이터 없이 정한 임시값이다. 설정값으로 두고, 운영하며 PAYMENT_PENDING 체류 시간과 "몇 번째 조회에서 풀렸는지"를 기록해 조정한다.

전제: 모든 회복 경로는 같은 결과 반영 경계(TX B)를 지난다. 그래서 경로끼리 겹쳐도 결과는 INV-002·INV-003이 지킨다. 회복 경로는 **결과를 확인하는 방법**일 뿐, 결과를 정하지 않는다(INV-004).

## 1. 미뤄진 결제의 네 가지 경우 (D-005)

| 경우 | 상황 | 결제 시도 | 조회 방법 | 계기 | 맡는 곳 |
|---|---|---|---|---|---|
| ⓐ 응답 유실 | create를 보냈는데 답을 못 받음 | UNKNOWN | 목록 (`providerOrderId`) | 우리가 timeout을 바로 겪음 | **같은 요청 안에서 바로 재조회** |
| ⓑ callback 유실 | 키는 받았는데 결과 알림이 안 옴 (안 옴, 사라짐, 받았지만 처리 실패) | 처리중 | 단건 (`transactionKey`) | **없음** | **스케줄러** (고객 reconcile도 열어 둠) |
| ⓒ 서버 재시작 | 발송 직후 우리 서버가 죽음 | 발송 시작 기록만 있음 | 목록 또는 단건 | 재시작 | **고객 reconcile, 스케줄러** |
| ⓓ PG에 안 들어감 | 발송 시작은 기록했는데 실제로 못 보냄 | UNKNOWN | 목록 → 계속 0건 | — | **관리자 확인** |

- ⓐ와 ⓑ의 차이: ⓐ는 우리 요청에 대한 **답**이, ⓑ는 나중에 PG가 보내는 **알림**이 사라진 것이다.
- ⓓ는 자동으로 풀 방법이 없다. 테스트 PG는 멱등 키를 받지 않아 다시 보낼 수 없고(INV-005), 0건은 실패의 증거가 아니다(INV-004). 그래서 사람이 확인한다(D-009).

## 2. ⓐ 바로 재조회

- 대상: create가 timeout·기타 오류로 끝나 UNKNOWN이 된 시도.
- 같은 요청 안에서 `providerOrderId` 목록 조회를 짧게 몇 번 한다. 확인되면 TX B, 아니면 UNKNOWN으로 202를 돌려준다.
- 실습 문서 예시: 조회 한 번 최대 1초, 총 3회, 사이 대기 100ms·200ms → 최대 약 3.3초. 실제 예산은 연결 풀·스케줄링까지 포함해야 한다.
- **우리 값 (D-028, 임시값):**

| 경로 | 조회 재시도 | 간격 | 고객 대기 상한 (대략) |
|---|---|---|---|
| confirm의 ⓐ 바로 재조회 | 최대 2회 | 100ms·200ms | create 응답 2초 + 조회 2 × 1초 + 0.3초 ≈ 5초 |
| 고객 reconcile | 최대 3회 | 100ms·200ms | 3 × 1초 + 0.3초 ≈ 3.3초 |
| 스케줄러, 수신함 워커 | 0회 (한 번만) | — | 고객이 기다리지 않음. `next_check_at`·`try_count`로 다시 한다 |

- 재시도는 한 층에서만 한다. 층마다 재시도하면 호출 수가 곱해진다.
- 구현 때 `maxAttempts`가 "처음 1회 포함"인지 Resilience4j 계약을 확인한다.

### timeout (D-025, D-030)

| 요청 | 연결 | 응답 | 재시도 |
|---|---|---|---|
| create | 1초 | 2초 | 없음 (INV-005) |
| 조회 | 1초 | 1초 | 위 표 |

`RestClient` + `JdkClientHttpRequestFactory`. timeout은 하위 JDK HttpClient에 건다. JDK HttpClient는 멱등하지 않은 요청을 기본으로 자동 재시도하지 않지만(`jdk.httpclient.enableAllMethodRetry` 기본 false), 실제 호출 수를 세는 테스트로 create와 조회 모두 확인한다.

## 3. 스케줄러 (D-006, D-007, D-008)

### 목표에서 수치를 역산한다

> 최악의 경우 결과 반영까지 ≈ **대상 기준 시간 + 주기 + 조회 시간**

| 숫자 | 값 (임시) | 근거 |
|---|---|---|
| 목표 | **5분** | 고객이 화면을 떠난 뒤 callback이 유실된 경우의 재고 묶임 허용 시간. 고객이 화면을 보고 있는 경우는 ⓐ와 고객 reconcile이 맡는다 |
| 대상 기준 시간 | **1분** | 발송 후 1분이 지나도 미종결인 시도만 본다. 정상 callback을 기다려 준다 |
| 주기 | **3분** | 1분 + 3분 + 조회 시간(최대 약 3.3초) ≈ 4분 남짓 |

30초 목표도 검토했다. 대상 기준 10초, 주기 15초면 숫자는 맞지만 하루 5,760번 돌고 정상 결제 상당수를 callback보다 먼저 조회한다. 예외 경로여야 할 스케줄러가 주 경로가 된다.

### 0건이 이어질 때

| 규칙 | 값 (임시) | 근거 |
|---|---|---|
| 관리자 확인 목록에 올리는 시점 (D-007) | **3번 연속 0건** (약 10분) | 너무 빨리 넘겨도 조회는 계속되므로 놓치는 시도가 없다. 틀려도 싸고 되돌리기 쉽다 |
| 조회 간격 늘리기 (D-008) | 처음 3번은 3분 → 30분 → 이후 2시간 | ⓓ는 영원히 0건이다. 고정 3분이면 시도당 하루 480번, 늘리면 첫날 약 20번·이후 하루 12번 |
| 미종결 조회 종료 (D-008) | 관리자가 처리하면 | D-009. 이후 아래 감시로 넘어간다 |

### 관리자 FAILED 처리 뒤 감시 (D-013)

| 숫자 | 값 (임시) | 근거 |
|---|---|---|
| 감시 기간 | **3일** | 짧게 틀리면 늦은 SUCCESS를 놓치고, 길게 틀리면 조회가 조금 늘 뿐이다. 그래도 3일에서 멈추는 건, 감시가 끝난 뒤에도 고객이 카드 승인 문자로 먼저 알고 문의하고 관리자가 단건 확인(D-014)으로 확인할 수 있기 때문이다 |
| 확인 간격 | **6시간** | 시도 1건당 12번 조회. 관리자 FAILED 처리는 ⓓ에서만 일어나는 드문 일이라 비용이 작다 |

감시 기간과 확인 간격은 스케줄러 주기(3분)와 다른 숫자다. 스케줄러는 3분마다 깨어나 "다음 확인 시각이 지난 시도"만 조회한다. D-008의 간격 늘리기도 같은 방식이다.

| | 짧으면 | 길면 |
|---|---|---|
| 감시 기간 (언제까지) | 놓칠 위험 ↑ | 조회 수 ↑ |
| 확인 간격 (얼마나 자주) | 조회 수 ↑ | 발견이 늦어짐 (놓치지는 않음) |

### 서버 여러 대

보류(`design.md` 8번). 여러 대에서 돌면 같은 시도를 중복 조회한다. 결과는 INV-002가 지키지만 PG 호출이 늘어난다.

## 4. Circuit breaker (PG 조회 경로에만)

### 이 경로에서 보호하는 것

circuit breaker는 아픈 PG를 매번 기다리는 손해를 없애는 장치다. 우리 스레드와 응답 시간, 회복 중인 PG를 보호한다. 4주차 Redis에서 같은 이유로 판단했다가 보류했다(`docs/week4/design.md` 8번).

OPEN은 "PG에 물어보지 못했다"이지 "결제 실패"가 아니다. OPEN 동안에는 저장된 상태와 "확인 불가"를 돌려주고 상태를 바꾸지 않는다(INV-004). 그래서 오탐이 나도 틀린 상태는 생기지 않고, 확정이 늦어질 뿐이다.

### 최소 표본: 큰 쪽으로 정한 근거

| | 오탐 (PG는 멀쩡한데 열림) | 늦게 열림 |
|---|---|---|
| 비용 | 틀린 상태 없음. 확정 지연, 그동안 온 callback은 조회 못 하고 버려짐 → 스케줄러가 회수 | 장애 중 조회는 거의 고객 reconcile뿐. 분당 10건 × 3.3초 ≈ 동시에 묶인 스레드 0.6개 |

동시에 묶인 스레드 수 ≈ 초당 요청 수 × 요청 하나가 기다리는 시간.

남은 문제: 최소 표본이 크면 호출이 드문 이 경로에서는 **거의 열리지 않는다.** 이 경로에서 circuit breaker의 의미 자체를 다시 봐야 한다.

### Resilience4j 기본값 (공식 문서 확인)

| 설정 | 기본값 |
|---|---|
| `slidingWindowType` / `slidingWindowSize` | COUNT_BASED / 100 |
| `minimumNumberOfCalls` | 100 (이만큼 쌓이기 전에는 실패율을 계산하지 않음) |
| `failureRateThreshold` | 50% |
| `waitDurationInOpenState` | 60초 |
| `automaticTransitionFromOpenToHalfOpenEnabled` | false (다음 호출이 와야 HALF_OPEN) |
| `permittedNumberOfCallsInHalfOpenState` | 10 |
| `maxWaitDurationInHalfOpenState` | 0 (탐색 호출이 다 찰 때까지 무한정 HALF_OPEN) |
| `recordExceptions` / `ignoreExceptions` | 비어 있음 (모든 예외가 실패로 기록됨) |

- **기록할 실패와 제외할 결과를 구분한다.** 단건 조회 404 같은 업무 결과를 실패율에 넣으면 정상 PG에서도 열린다.
- **데코레이터 순서:** Spring Boot 애너테이션 기본은 `Retry(CircuitBreaker(RateLimiter(TimeLimiter(Bulkhead(fn)))))`. Retry가 바깥이라 **재시도 하나하나가 표본 1건**이다. `retryAspectOrder`를 `circuitBreakerAspectOrder`보다 크게 주거나 함수형 체이닝으로 바꿀 수 있다.
### 우리 값 (D-029, 측정 전 임시값)

| 설정 | 값 | 근거 |
|---|---|---|
| 적용 대상 | PG 조회(단건, 목록)만 | 과제 규칙. create에는 걸지 않는다 |
| 창 | 횟수 기준 20건 | 장애 중에도 스케줄러와 수신함 워커가 조회해 몇 분 안에 찬다 |
| 최소 표본 | 20건 | "큰 쪽"으로 정한 판단. 기본값 100은 이 경로에서 사실상 열리지 않는다 |
| 실패율 | 50% | 기본값 |
| OPEN 대기 | 30초 | 스케줄러 주기(3분)보다 짧게. 다음 스케줄러 실행 때 탐색할 수 있게 |
| HALF_OPEN 탐색 | 3건 | 호출이 드물어 기본값 10건이면 회복 확인이 오래 걸린다 |
| 실패로 세는 것 | 연결·응답 timeout, 5xx | 단건 404와 빈 목록은 업무 결과라 뺀다 |
| 순서 | circuit breaker가 retry를 감싼다 | 조회 한 번(재시도 포함)이 표본 1건. 기본 애너테이션 순서와 반대라 adapter 안에서 데코레이터를 직접 조립한다 |

테스트에서는 최소 표본 2, 대기 1초처럼 작은 값으로 바꿔 CLOSED → OPEN → HALF_OPEN → CLOSED 전이를 확인한다. 테스트가 검증하는 건 동작이지 운영 수치가 아니다.

## 5. Bulkhead (보류)

한 의존성이 쓸 수 있는 **동시 실행 수**를 제한한다. circuit breaker는 과거(실패율)를 보고 실패가 쌓인 뒤에 열리므로 **첫 파도를 못 막는다.** bulkhead는 현재(동시 실행 수)를 보므로 첫 파도도 막는다.

| 방식 | 기본값 |
|---|---|
| `SemaphoreBulkhead` | `maxConcurrentCalls` 25, `maxWaitDuration` 0 |
| `ThreadPoolBulkhead` | 최대 스레드 = CPU 코어 수, core = 코어 수 − 1, `queueCapacity` 100 |

보류 근거: 과제 요구 범위 밖이다. 넣으면 넘친 callback은 거절되어 ⓑ가 되고, 스케줄러가 회수한다. **보호 장치는 일을 없애지 않고 회복 경로로 넘긴다.**

## 6. callback 수신함 (D-020, D-021)

callback은 수신함에 원문 그대로 저장하고 바로 200을 돌려준다. 조회와 TX B는 워커가 한다.

```
callback 도착 → 짧은 TX: 수신함에 1행 저장 (RECEIVED) → 200 "받아서 저장했다"
워커: RECEIVED·RETRY(next_try_at 지남) 행을 가져감
  → transaction_key / provider_order_id로 결제 시도 찾기
      ├ 못 찾음 → UNMATCHED (다시 시도 안 함)
      └ 찾음 → PG 권위 조회
           ├ 성공 → TX B → DONE (반영·중복 무변화·충돌 기록 모두 DONE)
           └ 실패(timeout, OPEN) → RETRY, try_count+1
                └ 3번 실패 → GAVE_UP → 그 시도는 스케줄러가 계속 확인
```

| 처리 상태 | 워커가 다시 가져가나 |
|---|---|
| RECEIVED | ✓ |
| RETRY | ✓ `next_try_at`이 지나면 |
| DONE | ✗ |
| UNMATCHED | ✗ 진짜 callback이면 INV-005로 시도가 먼저 존재하므로 다시 해도 같다 |
| GAVE_UP | ✗ 스케줄러가 안전망 |

- 우리 callback에는 이벤트 ID가 없어 같은 callback도 수신할 때마다 한 행이다. 중복 반영은 INV-002·INV-003이 결과 쪽에서 막는다.
- 본문의 `status`는 원문에 남기지만 판단에는 쓰지 않는다. 조회 결과와 나란히 보면 위조나 PG 쪽 이상을 알아챌 수 있다.

참고한 실무 계약:
- 토스페이먼츠: 10초 안에 200. 못 받으면 1·4·16·64·256·1024·4096분 간격으로 최대 7회, 마지막은 약 3일 19시간 뒤 (`docs.tosspayments.com/guides/v2/webhook`)
- Stripe: 복잡한 로직 전에 2xx, 이벤트는 비동기 큐, 처리한 이벤트 ID로 중복 거르기, live 모드 최대 3일 재전송 (`docs.stripe.com/webhooks`)

검토하고 고르지 않은 것:
- **동기 처리:** 조회가 막히면 callback이 버려진다.
- **한 트랜잭션 안에서 비동기 처리:** 쓸 수 없다. Spring 트랜잭션은 스레드에 묶여 있어 `@Async` 작업은 그 트랜잭션에 속하지 않는다. TX 안에서 PG를 기다리는 것도 과제 규칙 위반이다. commit 뒤 비동기는 할 일이 메모리에만 있어 재시작하면 사라진다.
