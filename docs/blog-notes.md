# 기술 블로그 소재 후보

Technical Writing Quest("이번 주 이해가 달라진 주제 하나를 자신의 코드와 함께 설명")용 후보를 모아둔다. 여기서 하나를 골라 실제로 쓴다 — 이 파일 자체가 블로그 글은 아니다.

형식: 상황 → 그때 든 생각/판단 → 근거 → 왜 소재가 되는지.

---

## 좋아요 비동기 처리, 알지만 지금은 안 만들기로 한 판단

**상황**: 이벤트스토밍 때 "좋아요 수 집계를 GROUP BY로 하면 부하가 커지면?"이라는 핫스팟을 스스로 남겼었다. 설계를 진행하며 이게 "고빈도 쓰기/읽기를 동기 경로에서 분리해 비동기(이벤트 기반)로 처리하는 문제"라는 걸 구체적으로 이해하게 됐다.

**판단**: 지금 과제 규모(로컬 실습, 실제 트래픽 없음)에서는 이 문제가 만들지 않을 이유다.

**근거**:
- 실습 문서 어디에도 비동기·성능 요구사항이 없다.
- 이 저장소에 이미 `commerce-streamer`/`kafka` 모듈이 존재한다 — 이건 나중 라운드의 몫이라는 신호다.
- "아직 요구하지 않은 범용 재고 엔진을 만들지 않기"(발제, TDD 섹션)와 같은 원칙 — 필요하지 않은 인프라를 미리 만드는 건 과잉설계다.
- 핫스팟은 원래 "지금 결정하지 않고 미뤄두는 것"이라는 표시다.

**왜 소재가 되는가**: "몰라서 안 만든 것"과 "알고도 지금은 안 만들기로 판단한 것"의 차이를 보여줄 수 있다. 판단 기준(트리거 조건: 트래픽 패턴, 팀 구조 등)까지 설명하면 단순 기능 구현기가 아니라 설계 판단 과정을 다루는 글이 된다.

## 통합테스트가 실제로 잡아낸 버그 — 포인트 충전이 2배로 반영되던 문제

**상황**: 동시성 대응으로 `Point.charge()`를 원자적 UPDATE(`SET balance = balance + amount`)로 구현했는데, 통합테스트에서 "1000원 충전했더니 2000원이 됐다"는 결과가 나왔다. Docker/Testcontainers가 여러 세션에서 동시에 돌면서 계속 인프라성 실패만 내고 있었던 탓에, 이 진짜 버그가 한동안 "또 인프라 문제겠지"에 가려져 있었다.

**판단**: 실패 로그의 Hibernate SQL을 직접 읽어서 원인을 추적했다 — `update user set point_balance=?` 한 줄이 원자적 UPDATE 직전에 끼어 있었다. `UserService.chargePoint()`가 self-invocation(`this.getUser(id)`)으로 `@Transactional(readOnly=true)`를 무시하게 만들었고, 그 결과로 넘어온 매니지드 엔티티에 `charge()`를 호출해 메모리 값을 바꿔놨더니, 원자적 UPDATE 쿼리 실행 직전에 Hibernate가 그 변경을 먼저 flush해버린 것이었다.

**근거**: 매니지드 엔티티 변경 + 원자적 SQL을 같은 트랜잭션에서 섞어 쓰면, "엔티티 기반 변경"과 "SQL 직접 조작" 두 전략이 auto-flush를 통해 서로 간섭한다. 검증만 필요한 곳은 영속화되지 않은 새 인스턴스에 대고 실행하고, 원자적 쿼리엔 `@Modifying(clearAutomatically = true)`를 붙여 영속성 컨텍스트를 비우는 것으로 고쳤다.

**왜 소재가 되는가**: "동시성 문제를 원자적 UPDATE로 막았다"까지만 다루면 흔한 글이 되지만, "그 해법 자체가 JPA의 다른 메커니즘(auto-flush, self-invocation)과 부딪혀서 새로운 버그를 만들었고, 테스트가 그걸 잡아냈다"는 이야기는 "동시성 제어 기법을 안다"와 "그걸 기존 프레임워크 관례(엔티티 기반 변경) 위에 안전하게 얹을 줄 안다"가 다른 능력이라는 걸 보여준다. 특히 인프라 노이즈(Docker 경합) 속에서 진짜 버그를 가려내는 판단 과정 자체도 소재가 된다.
